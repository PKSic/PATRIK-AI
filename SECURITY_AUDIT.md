# Отчёт по информационной безопасности и архитектурному аудиту PATRIK AI

**Автор:** PKSic  
**Проект:** Веб-сервис управления подписками и агрегации нейросетевых API «PATRIK AI»  
**Дата аудита:** 12 ноября 2026 г.  
**Стек:** Node.js, Express, PostgreSQL 16, React 19, TypeScript  

---

## 1. Введение и цели аудита

Целью настоящего аудита являлось выявление и устранение архитектурных и практических уязвимостей в клиентской и серверной частях сервиса, защита конфиденциальных данных пользователей, аутентификации, биллинга, работы с базой данных PostgreSQL и интеграции с платёжными эквайрингами.

Анализ проводился в соответствии со стандартами OWASP Top 10 (A01:2021 — Broken Access Control, A02:2021 — Cryptographic Failures, A03:2021 — Injection, A04:2021 — Insecure Design, A07:2021 — Identification and Authentication Failures).

## 2. Результаты анализа подсистем и архитектурные решения

### 2.1. Аутентификация и управление паролями
- **Метод хеширования:** Пароли пользователей ни при каких обстоятельствах не хранятся в открытом виде. Для защиты применяется функция формирования ключа `scrypt` (`crypto.scryptSync`) с уникальной криптографической солью длиной 16 байт (`crypto.randomBytes(16)`), генерируемой индивидуально для каждого пользователя.
- **Формат хранения:** `соль_hex:хеш_hex`.
- **Защита от атак по времени (Timing Attacks):** При верификации введённого пароля хеши сравниваются с помощью функции `crypto.timingSafeEqual`, предотвращающей утечку информации о длине и совпадении байтов через задержки ответа.
- **Защита от Rainbow Tables:** Использование криптостойкой соли делает невозможным применение предвычисленных таблиц и словарных атак.

### 2.2. Сессии и авторизация (Middleware `requireAuth`)
- **Механизм токенов:** Реализована stateless-модель сессионных токенов на базе симметричного шифрования `AES-256-GCM` и HMAC-SHA256 подписи.
- **Структура токена:** Токен шифрует идентификатор пользователя, email и временную метку истечения срока жизни (`exp`).
- **Верификация:** Middleware `requireAuth` извлекает заголовок `Authorization: Bearer <token>`, расшифровывает полезную нагрузку и проверяет срок валидности (`Date.now() < exp`). Если токен подделан, повреждён или просрочен, запрос прерывается со статусом `401 Unauthorized`.
- **Разграничение прав (RBAC):** Для административных функций реализован middleware `requireAdmin`, проверяющий роль пользователя (`role === 'admin'`) и принадлежность email белому списку администраторов.
- **Предотвращение IDOR:** Все операции с подписками, транзакциями и API-ключами изолированы в контексте `req.user`, исключая доступ к чужим ресурсам через подмену идентификаторов.

### 2.3. Биллинг, платёжный шлюз и защита Webhook
- **Исключение клиентского подтверждения:** Клиентское приложение лишена возможности самостоятельно подтверждать оплату. Эндпоинт `POST /api/subscribe` возвращает клиенту только параметры сессии (`sessionId`, `tx_code`, `amount`). Секретная цифровая подпись HMAC клиенту **никогда не выдаётся**.
- **Процесс оплаты через шлюз:**
  1. `POST /api/subscribe` создаёт транзакцию со статусом `pending` (`Ожидает оплаты`), регистрирует её в постоянном хранилище и возвращает сессию.
  2. Внешний платёжный шлюз (Банк, ЮKassa, СБП) принимает платёж от пользователя и отправляет серверный HTTP POST запрос на защищённый роут `POST /api/webhooks/payment` с заголовком `X-Signature`.
  3. Сервер рассчитывает контрольный HMAC-SHA256 от параметров транзакции с использованием секретного ключа `PAYMENT_WEBHOOK_SECRET` и сравнивает его через `crypto.timingSafeEqual`.
  4. При успешной валидации статус транзакции меняется на `Оплачено`, фиксируется `paid_at`, а подписка пользователя переходит в состояние `active`.
  5. Для защиты от повторного проведения одного и того же платежа (Replay Attack) внедрён реестр `processedWebhooks`: дублирующиеся уведомления отклоняются с кодом ответа `already_processed`.
- **Постоянное хранение платёжных сессий:** Все ожидающие платежи сохраняются в постоянном хранилище (PostgreSQL таблица `transactions` со статусом `pending` и файл `patrik-store.json`), что исключает их потерю при перезапуске сервера или масштабировании.
- **Защита от Race Condition:** На время оформления и обновления подписки email пользователя блокируется в коллекции `inFlightSubscriptions`. Параллельные запросы от одного аккаунта отклоняются со статусом `409 Conflict`. Блокировка гарантированно снимается в блоке `finally`.

### 2.4. Защита базы данных PostgreSQL и целостность схемы
- **Полное соответствие схемы и запросов:** Все SQL-запросы в серверном коде синхронизированы со схемой `database/schema.sql` (`password_hash`, `full_name`, `role`, `created_at`).
- **Изоляция запросов:** Обращения к СУБД PostgreSQL через библиотеку `pg` используют строго параметризованные запросы (`$1, $2, ...`). Прямая конкатенация строк исключена (защита от SQL Injection).
- **Транзакционность (ACID):** Обновление статусов платежей и активация подписок выполняются в рамках транзакций PostgreSQL (`BEGIN`, `COMMIT`, `ROLLBACK`).
- **Явная обработка ошибок:** Скрытое подавление ошибок СУБД устранено. В случае сбоя при записи пользователя или транзакции сервер прерывает операцию и возвращает клиенту HTTP статус `500 Internal Server Error`.
- **Каскадное удаление:** В схеме `database/schema.sql` настроены внешние ключи `FOREIGN KEY ... REFERENCES users(id) ON DELETE CASCADE`. При удалении учётной записи пользователя PostgreSQL автоматически удаляет все связанные с ней подписки, API-ключи, транзакции и логи.

### 2.5. Реальная обработка AI-запросов и аудит расхода токенов
- **Эндпоинт инференса `POST /api/v1/chat/completions`:** Реализован API-шлюз, принимающий запросы с авторизацией по API-ключам `Bearer sk-patrik-...`.
- **Контроль квот:** Перед генерацией проверяется активность подписки пользователя и остаток токенов (`token_limit - tokens_used`).
- **Списание токенов:** Рассчитывается точный объём токенов промпта и ответа модели, значение инкрементируется в подписке пользователя и персональном ключе.
- **Журналирование в `usage_logs`:** Каждый вызов API фиксируется в таблице `usage_logs` с указанием пользователя, модели, числа токенов и рассчитанной стоимости.

### 2.6. Реальный замер задержки сети (Ping)
- В интерфейсе устранена случайная симуляция задержки.
- На бэкенде внедрён легковесный эндпоинт `HEAD /api/health`.
- Фронтенд измеряет фактический Round-Trip Time (RTT) сетевого запроса в миллисекундах (`performance.now()`) при загрузке страницы, по таймеру каждые 10 минут, а также по клику пользователя на индикатор.
